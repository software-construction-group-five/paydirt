What’s left to build

Tasks grouped by branch, with the order they need to happen.

Original baseline: develop at c1fe551 · Updated for PR12 enemy AI and combat phases 1–3 · November 11, 2026

Where things stand

The map generator, screens, settings, stats, inventory storage, equipment slots, and basic enemy types exist. Level entity storage, depth-based populations, line of sight, exploration memory, and themed population rendering are implemented on feature/level-entities.

Game owns an active Player and MessageLog. Movement, waiting, bump-to-open doors, enemy collision checks, movement-driven visibility, and player rendering are implemented. Player bump attacks, weapon effects, enemy defeat/removal, and rare equipment drops are implemented. PR12 AI decisions and one enemy phase per spent action are integrated with terrain line of sight. Enemy damage, automatic effect ticks, inventory controls, floor changes, and player death handling remain unfinished.

These are suggested branches. Build on the existing work. Some gameplay rules below still need a team decision.

Work order

1. Start player-movement and level-entities together.
2. Then work on enemy-ai, inventory-gameplay, and floor changes in parallel.
3. Connect combat-turns after movement, entities, and AI are ready.
4. Finish death handling after combat.
5. Test everything together in integration/gameplay.

You can plan rules and build small pieces early. Finish each branch only after the parts it depends on are working together.

Shared rules

  • Every gameplay action uses one turn: moving once, attacking once, waiting, picking up or dropping an item, equipping or unequipping, opening a door, and using an item. Failed attempts also use a turn. Screen redraws and menu navigation are not gameplay actions.
  • Level tracks a stable ID for each enemy. Game uses that ID to read its position, health, and state. AI chooses a move; Game checks it and updates the position. Dead enemies are removed from Level and cannot act or appear again.
  • Stairs require the player to press > while standing on them. Stepping onto stairs does not descend. A dead player cannot interact with stairs.

Several branches change Game, Player, actions, keybindings, and display data. Keep those edits small and merge often. Combat owns the turn loop; other branches report what the player did.

Undecided

  • Consumable effects and healing values remain to be defined. Weapon damage dice, armor defense bonuses, and weapon on-hit effects are specified in the combat contract; initial balance values require playtesting.
  • Item catalog: which items, armor, and weapons will be added to the game?

feature/player-movement

Put the player in the game and let them move.

Status: Implemented and integrated with level-entities. Bumping an enemy attacks without moving; lethal hits remove it immediately. Bumping a closed door opens it without moving; entering takes another action. Movement and door opening refresh visibility. Moves and waits report spent turns, including failed attempts; the shared turn loop remains combat-turns work.

  • Start a game (SDD Contract 1)

    Store the active Player and MessageLog in Game. On New Game, generate a floor, create starting stats, inventory, and equipment, and set the player position to the floor’s start. Clear the previous session’s messages and selections.

  • Add controls (SDD Contract 21)

    Add left, right, and wait to Action and the input action-name mapping. Add their playing keybindings. Build help text from those bindings.

  • Move safely (SDD Contracts 2, 7, 9, 10)

    Game calculates the target tile from the player position and direction. If the tile is outside the map or blocked by terrain, leave the position unchanged. Ask Level whether an enemy occupies the target. Occupied targets dispatch a player attack without moving; defeated targets are removed immediately. Otherwise update Player’s position.

  • Open doors (SDD Contracts 2, 8, 9)

    Level provides an operation that changes a closed door to an open door. Game calls it when the player bumps the door and refreshes visibility. Opening reports one spent turn and leaves the player in place; entering takes another action.

  • Show the player (SDD Contracts 6, 20)

    Read position and health from Player and pass them to the existing display views. Center the map view on that position. Pass MessageLog entries to the message panel.

  • Report spent turns (SDD Contract 2)

    Return an action result that tells the shared turn loop to advance once for a move, wait, or door action, even if it fails. Pause, menu navigation, and redraws do not advance the turn.

Done when

  • A new player appears at the start and moves in all four directions.
  • Walls, map edges, closed doors, and enemies are handled correctly.
  • Pause keeps the player and floor unchanged.

feature/level-entities

Put enemies and items on each floor.

Status: Implemented and covered by automated checks. Player collision and movement-driven visibility updates are integrated through player-movement; AI, combat, and inventory controls remain separate features.

  • Store enemies and floor items (SDD Contracts 10, 11)

    Implemented: Level owns enemies keyed by stable floor-local EnemyId and ground items as owned Item/Position entries. Position remains in Enemy; IDs are never reused within a floor.

  • Add collection operations (SDD Contracts 10, 11, 13)

    Implemented: borrowed iteration, ID and tile lookup, validated insertion/movement, and ownership-preserving removal. Unknown IDs return missing results without changing storage. Ground items support tile lookup and selected-entry removal; indices shift after removal, and runtime items may share tiles.

  • Check occupied tiles (SDD Contracts 9, 10)

    Implemented: terrain walkability is separate from occupancy. Level rejects out-of-bounds, blocked, or enemy-occupied targets; staying on the current tile succeeds. Game remains responsible for checking the active player before applying an enemy move.

  • Spawn real enemies and items (SDD Contracts 10, 11, 18, 19)

    Implemented: generation stores enemies and catalog items on distinct ordinary floor tiles, excluding stairs, obstacles, and the entire starting room. Species unlock at zero-based depths 0 (Slime), 2 (Ghost), and 4 (Goblin); depth-dependent weights increasingly favor stronger species.

  • Handle limits (SDD Contract 19)

    Implemented: bounded counts consume shuffled spawn candidates without replacement, reserving item space on cramped floors. Every random choice uses the supplied RNG. Catalog level one is available at depth zero using saturating depth + 1. Tests cover reproducibility, empty/exhausted candidates, species minimum depths, placement restrictions, maximum depth, and increasing average difficulty.

  • Draw the population (SDD Contracts 12, 20)

    Visibility backend implemented: Tile owns seen and visible flags; Level.update_visibility(player_position) refreshes sight while retaining exploration memory. New Game initializes sight from the start. Rendering implemented: Renderer builds themed display entries from visible_enemies() and visible_ground_items(). Unseen terrain is blank, seen terrain stays drawn, and entities require current tile visibility. Optional species/category theme entries default for older configurations. Drawing order is terrain, items, enemies, then the player when supplied; the launcher supplies the active player position for drawing and camera focus.

Done when

  • Generated floors contain valid enemies and items.
  • Initial enemy spawns do not overlap each other, items, the starting room, or stairs; runtime movement uses separate rules.
  • Enemy IDs stay stable after other enemies are removed. Lookup, movement, and removal affect only the intended enemy.

feature/enemy-ai

Make enemies react to the player. Use the states defined in Enemy: Idle, Attacking, and Fleeing.

Status: PR12 merged from develop (de0d21d). Species profiles, chase/flee decisions, and spent-action AI scheduling are implemented. Merge reconciliation adds terrain line of sight, keeps scaled health/flee thresholds and cardinal attacks, and preserves player combat/drop handling. Enemy damage remains combat-turns work.

  • Define each enemy’s behavior (SDD Contract 13)

    Species detection ranges are Slime 3, Ghost 6, Goblin 5 (Chebyshev tiles). Detection also requires Map line of sight, including adjacent corners. Outside range or sight, enemies wait Idle; detected enemies below their exclusive scaled threshold flee. Healing above threshold ends fleeing on the next decision.

  • Choose a legal move (SDD Contracts 9, 13)

    AI proposes a legal cardinal step that improves Manhattan distance, trying alternatives and waiting if blocked. Game revalidates terrain, enemy occupancy, and player occupancy before Level movement. Enemies do not open doors or perform full pathfinding.

  • Request attacks (SDD Contracts 2, 13, 14)

    AI returns Wait, Move with a target, or Attack. Attacks require cardinal adjacency; diagonal neighbors approach. Game applies one AI decision per living enemy after each spent action. Attack damage remains combat-turns work; AI does not mutate health or advance turns.

  • React to damage (SDD Contracts 10, 13)

    Health changes mark low-health enemies Fleeing and dead enemies Idle without waking healthy idle enemies. AI recomputes state using range, sight, and health each turn. Game removes defeated enemies immediately through the shared defeat/drop path. Signed health changes remain negative for damage.

Done when

  • Enemies notice, approach, attack, and flee under the agreed rules.
  • Blocked paths and nearby enemies do not cause illegal moves.
  • Game controls when decisions happen and how damage is applied.

feature/combat-turns

Resolve attacks and advance the game one turn at a time.

Status: Phase 1 foundation is implemented: scaled stats, equipment modifiers, reusable weapon effect specifications, effective-stat queries, enemy effect operations, cardinal range queries, and AI intents. Combat and turn contracts specify combat rules and the remaining turn loop, enemy attacks, descent timing, and game-over message history. Phase 3 implements player bump attacks, immediate enemy defeat/removal, messages, and rare depth-appropriate equipment drops. Connect the full loop after movement, entities, and AI; coordinate item data with inventory-gameplay.

  • Set damage rules (SDD Contracts 2, 14)

    Implemented: independent weapon damage dice (d4, d6, d12), a starting equipped 2d4 Pickaxe, and max(1, rolled damage − effective defense). Player HP is 40; Slime/Ghost/Goblin HP is 8/14/24 with 1d4/1d6/1d12 damage rolls. Cardinal bump attacks keep the player in place; weapon effects remain supported. Messages omit enemy IDs. The combat contract defines turn order, death/drop behavior, descent, and interface responsibilities. Implement these rules in the remaining phases.

  • Apply attacks (SDD Contracts 2, 7, 10, 13, 14)

    Phase 2 primitives implemented: pure attack damage calculation and Level damage/effect operations by EnemyId, with actual HP loss, death status, and effect application outcomes. Missing IDs are unchanged; lethal hits skip on-hit effects; removal remains Game’s responsibility. Phase 3 connects player bump attacks, weapon effects, actual-damage messages, immediate defeat/removal, and the shared 5% equipment-drop path. Still needed: connect enemy attack decisions and schedule turns/effect deaths.

  • Run one turn loop (SDD Contract 2)

    PR12 already schedules one enemy decision phase after each spent player action. Extend this existing boundary with enemy attack damage and status-effect updates in the agreed order; do not add a second enemy loop. Menu navigation, pause, and redraws skip this loop. Item actions call this same loop instead of running a second one.

  • Handle failed actions (SDD Contract 2)

    Return a spent-turn result for blocked movement, failed pickup, full-inventory rejection, and failed item use. Leave rejected changes unapplied, then run the normal turn updates once.

  • Use effects and equipment (SDD Contracts 2, 7)

    Tick player effects, then surviving enemies’ effects once per ordinary turn. New weapon-applied effects tick that turn. Roll equipped weapon dice (or unarmed 1d4) once and calculate defense from base stats plus equipped armor. All initial flat attack modifiers are zero. Reading stats or drawing a frame must not change base values or add bonuses again.

  • Stop on death (SDD Contracts 2, 5, 10)

    After each damage or effect update, check the player’s health. At zero health, stop remaining processing and end the session through progression-gameover, preserving the message history for game-over viewing. Skip enemy IDs that Level no longer contains. Resolve direct and effect enemy deaths through one removal/drop path with a single 5% equipment-drop roll and depth-appropriate catalog selection.

Done when

  • Attacks, defense, equipment, and lethal damage work together.
  • Every spent turn advances enemies and effects exactly once.
  • Menus and redraws spend no turns; dead actors do not act.

feature/inventory-gameplay

Let the player pick up, manage, equip, and use items.

When: Start item rules now. Controls need Game to own a Player. Pickup/drop needs level-entities. Work alongside AI and combat, using the shared one-action, one-turn rule.

  • Make carried items selectable (SDD Contract 17)

    Add borrowed access to Inventory’s items for display and selection. Track a selected carried entry separately from its catalog index so duplicate copies stay distinct. After removal, clamp the selection to the remaining entries; handle an empty list.

  • Add inventory controls (SDD Contracts 3, 17, 20, 21)

    Add open, select, use, equip, unequip, drop, and back actions with screen-specific bindings. Game stores the inventory selection and changes screens. Build inventory display rows from carried items and equipment slots.

  • Pick up and drop (SDD Contracts 11, 15, 16)

    For pickup, check the category limit before transferring the selected ground Item from Level to Inventory. On rejection, keep it on the floor. For drop, transfer the selected carried Item to Level at the player position. Transfer the existing object rather than recreating it from its catalog index.

  • Equip and unequip (SDD Contracts 7, 15, 16)

    Add Player operations that transfer a selected carried item into its equipment slot and return the displaced item to Inventory. Unequip transfers an item back to Inventory. Check capacity before changes; on failure, preserve both inventory and equipment.

  • Define item effects (SDD Contract 18)

    After the Undecided choices are settled, add the chosen catalog entries, spawn levels, and effect data to Item. Use that data for equipment modifiers and consumable effects. Define a clear result for invalid catalog lookup.

  • Use items and show results (SDD Contracts 2, 7, 16, 20)

    Apply the selected consumable’s effect and remove exactly one copy according to the agreed use rules, including use at full health. Rebuild inventory/status display data and append a result message. Pickup, drop, equip, unequip, and use each advance one turn, even on failure.

Done when

  • Pickup, drop, swap, unequip, and use preserve every item correctly.
  • Full categories and duplicate copies behave correctly.
  • Equipment and consumables affect gameplay, and controls match the help.

feature/progression-gameover

Move between floors and finish a session.

When: Start stairs after player-movement. Finish populated floors after level-entities, death handling after combat, and state-preservation checks after inventory.

  • Use stairs (SDD Contracts 2, 4, 21)

    Map > to a descend action. Game checks that the player is alive and their position equals Level’s stairs position before descending. Moving onto stairs does not descend. Valid descent ticks player effects on the old floor; death prevents replacement. Otherwise enter the new floor without enemy actions or enemy effect ticks. Failed descent spends an ordinary turn.

  • Generate the next floor (SDD Contracts 4, 7, 19)

    Generate a Level at the next depth using Game’s RNG, replace the old Level, and set the existing Player’s position to the new start. Keep the player’s stats, effects, inventory, and equipment. Check depth overflow before incrementing.

  • Show game over (SDD Contracts 5, 20)

    When combat or a status effect reduces player health to zero, store final depth and cause of death in session-summary state. Set Screen to GameOver and reject gameplay actions. Pass the stored summary and full MessageLog history to the game-over view, showing recent messages initially and allowing history scrolling without spending turns.

  • Return and restart (SDD Contracts 1, 3, 5)

    On return to menu, clear active session state. On New Game, create a new player, floor, log, and selections, and clear the old summary. Route quit through the launcher’s existing terminal cleanup.

  • Keep stair use separate from movement (SDD Contracts 2, 4, 5)

    Only the descend action can replace the floor. Reject it for a dead player. Remove the old floor’s pending enemy actions when replacing Level. Death on a stairs tile follows normal death handling. Add a win condition only if required.

Done when

  • Descent keeps player health, effects, inventory, and equipment.
  • Attack and effect deaths both show correct results.
  • Restart creates a fresh session without leftover state.

integration/gameplay

Merge the features and check a complete game.

When: Merge and check changes throughout development. Final checks need all six feature topics.

  • Merge in order

    Merge movement and entity storage first, then AI and inventory. Add the shared combat loop, then complete death handling. Update each dependent branch after its required branches merge.

  • Check every screen (SDD Contracts 20, 21)

    Test display data for player/enemy/item positions, health, equipment, inventory, messages, and results. Check small/resized terminals, theme changes, and remapped controls. Decide whether full message history needs a separate view.

  • Play a full session (SDD Contracts 1–21)

    Add integration checks that send actions through Game: start, move, open a door, attack, pick up, equip, use, pause, descend, die, and restart. Assert positions, health, item ownership, depth, and screen after each step. Include rejected actions and effect damage.

  • Check timing and cleanup (SDD Contracts 2, 21)

    Check that each gameplay action advances one turn and redraws/menu navigation advance none. Check configuration errors before terminal setup and terminal restoration after normal and error exits.

  • Update the documents

    Update SDD descriptions when implemented behavior or interfaces differ. Follow the SCM plan’s documented issue, review, baseline versioning, recovery, and audit procedures. List any remaining unfinished features.

  • Run final checks

    Run relevant tests, formatting checks, and Clippy. Fix failures, stale TODOs, and missing public documentation. Follow the project’s pull-request rules.

Done when

  • A complete session works through normal keyboard input.
  • All features work together without lost items or extra turns.
  • Tests and project checks pass, and documents match the game.
